## 产品范围

目标用户假设：了解部分基础规则、希望理解短战术与常见走子错误的象棋初学者。该假设尚需真实访谈确认，不应写成已经验证的用户需求。

核心任务：用户选择一个短局面，自行走棋；软件检查合法性与明确训练目标；卡住时提供分级提示；完成后展示规则证据和讲解；错误进入错题本供再次练习。

领域知识：基础走子、马腿与象眼、炮架、过河兵、应将、绝杀与困毙区别。资料来源为固定上游规则实现与本项目自编教学案例；不是凭空注明某本教材的摘录。

定制方法：确定性标签检索知识条目、规则工具调用、Pikafish UCI 调用、教学提示编排、结构化输出校验。未使用微调或向量数据库，不称为已经完成模型训练。

## 代表性演示

1. 炮架题：炮不能落在隔子后的空点，隔一个炮架吃到目标才通过。
2. 马腿题：一个方向受阻不等于所有方向都受阻。
3. 多解将杀：`pawn-mate` 的三种实际将杀均通过。
4. 困毙反例：`cannon-mate` 中 `d7c7` 导致困毙，虽然是象棋胜局，却没有完成本题明确的“绝杀”目标。

## 定制效果检查方案（尚未执行真实模型评测）

基础条件与定制条件采用同一模型、同一候选着法、同一规则证据与同一次引擎分析。定制条件另加入相关规则条目、自编教学案例和教学表达要求。每个案例先保留原始输出、模型名、时间、调用量与校验状态，再请实际用户/评审根据事实正确性、着法一致性、证据支持度和可理解性评价。

不根据 JSON 校验通过就声称教学质量提高；不把界面更美观当作模型能力提升；无真实输出时不填写效果百分比。

## 尚需真实补齐的作业材料

- 调研：访谈实际初学者和有经验的棋友，记录遇到的具体困难、现有替代方式和反馈；不代造访谈记录。
- 团队：队名、全部成员资料、首次合照、50–100 字愿景、实际分工。
- 需求文档：依据《软件需求规范》组织迭代表、调研、用户场景、标志、思维导图、类图、功能和验收标准；当前标志已有 SVG，其他正式图件与完整文档后续制作。
- 答辩：10 分钟演示及 6 分钟问答准备，核心证据来自真实运行与调研。
- 博客：团队博客一篇，规定标题、开头课程/作业/目标/团队/成员表；本轮未编写或发布。
- 最终交付：扩展真实模型和对照案例，公开部署并提供检查方式。
