## 一、前期工作总结与思考

第一次团队作业确定了目标用户和练习场景。棋理学伴面向已经会基本走棋、希望练习短局面战术的象棋初学者，核心场景是「先走一步，再弄清为什么」。早期运行版已有教学题、规则判定、分级提示和错题记录，也能提供 Pikafish 参考线路和模型讲解。这个基础让我们可以把需求落实到具体的一道题，观察从落子到重练之间是否还有断点。[团队展示与选题报告](https://www.cnblogs.com/Bari320/p/23419835)

第二次团队作业把需求画成了训练、讲解、导入和管理端的交互原型，也梳理了前端、规则模块、引擎、模型和数据的职责。原型让我们可以在开发前讨论误走、加载和失败时的操作。接下来需要用同一条任务路径走查原型和运行版，特别关注小屏上的操作顺序，以及用户失败后能否继续完成任务。[项目原型设计与概要设计](https://www.cnblogs.com/Bari320/p/23595242)

前期试做也暴露出几处问题，需要在本轮改进中优先处理。

- **训练反馈要指向下一次尝试。** 「走法非法」和「走法合法但没达到题目目标」对应不同的学习问题。如果回放时棋盘已经切到下一步，证据还停在上一步，用户也很难理解刚才的反馈。已有的判定和回放需要用多解题、连续将杀题和切题场景一起检验。
- **个性化教练需要准确的复盘上下文。** 档案可以调整讲解难度和节奏。要解释用户某一次选错了什么，还需要把本题的最近尝试、提示记录、自动应将和当前棋盘一起交给教练。讲解是否更容易理解，需要结合初学者能否复述理由、能否把同样的方法用到下一题来判断。
- **识图准确性需要人工核对的入口。** 前期真实联调时，黑马被识别到了相邻一格，误识后的局面仍能通过规则检查。原图对照和摆棋修正应当放在求解之前。遇到不适合识别的图片，用户可以改用手动摆棋或粘贴 FEN 局面串。[前期图片联调记录](https://github.com/Ther-ux/qili/blob/main/docs/IMAGE-ENDGAMES-REAL-VALIDATION.md)
- **启动步骤影响他人能否复现。** 前期源码包要求使用者自行安装 Node.js。答辩和伙伴试用时，换到一台没有预配置环境的 Windows 电脑，就需要重新准备依赖。本轮拟提供便携包并在干净环境下演练启动、走棋和回放。

## 二、改进方案与验收标准

先用训练、提示、回放和错题重练检验学习流程，再联调教练和导入。布局、原型及便携包用同一组题目走查，便于比较用户在不同入口能否完成同一个任务。

| 编号 | 拟采取的改进方案 | 计划怎样验收 |
| --- | --- | --- |
| A1 规则、题库与训练闭环 | 统一非法、合法但未达目标、独立完成和提示后完成四种反馈。为多解、连续将杀和困毙补充回归场景，串起错题标记、重练及学习记录备份。 | 用炮架题对照非法着法与正确走法。用多解和连续将杀题检查合法解、自动应将及最终通关条件，再从错题页完成重练。运行 `npm run verify` 校验 20 道教学题。 |
| A2 解法回放与自由摆谱 | 沿用走前、走后及分支回放。把核验结果与当前局面绑定，并在换题、重试和继续走棋时核对提示清理及迟到响应的处理。 | 在车兵残局的末步核对行棋方、合法着法数和终局结论。切入摆谱分支或另一道题后检查证据归属、旧讲解清理和训练成绩。 |
| A3 个性化教练与结构化棋盘 | 沿用教练档案和固定红方坐标，重点核对训练、导入和自由摆谱三处得到的局面证据。检查服务端重验近期尝试时是否取到了当前题、当前分支和提示记录。 | 验证翻转时 `a0` 的棋盘位置含义保持一致，并检查换题隔离、自动应将、档案保存和讲解失败。用同一模型、局面和棋局证据比较基础讲解与个性化讲解，记录试用者能否复述要点并独立完成后续练习。 |
| A4 图片、FEN 与手动摆棋 | 从已有的四角校准和人工改棋流程出发，走查确认前的每一步，并补强草稿恢复、主动取消和重试。识别失败时保留 FEN 和手动摆棋入口。 | 用曾出现识图偏差的棋盘复现「选图、校准、纠正、确认、分析」，再走一遍不调用模型的 FEN 分析。检查刷新、取消，以及结果中对已证明短将杀和引擎参考路线的标注。 |
| A5 训练页布局与可访问性 | 让题目目标和棋盘占据主操作区，把分类和题库归到同一入口，教练偏好放入独立设置弹窗。补齐键盘选子、落子、取消和焦点提示。 | 桌面和窄屏分别完成选题、走棋、看提示和复盘。仅用键盘完成选子与落子，检查翻转后坐标和关闭弹窗后的焦点位置。 |
| A6 高保真原型与交互说明 | 用 Evolus Pencil 补全桌面和移动端的主要路径、等待和失败状态，整理操作规则、可编辑工程和可离线预览的版本。管理端通过原型走查题库、知识管理和 Agent 审查。 | 打开 `.epgz` 和离线播放器，分别走查一次训练、导入失败和管理端流程，确认页面跳转、反馈和返回入口。 |
| A7 便携打包与发布 | 把 Node.js、Pikafish 和权重随 Windows x64 包交付，配套一键启动、网络与模型配置说明。将最终源码、验证记录和答辩材料关联到对应版本。 | 在无需预装 Node.js 的 Windows 环境解压启动，尝试默认端口占用场景，并在无模型配置时完成练习、回放和手动残局分析。 |

## 五、测试与交付安排

- **测试。** 提交前运行 `npm test` 和 `npm run verify`。模型接口的自动回归使用模拟响应，真实识图和教学试用单独记录。人工走查按第二节的任务路径记录操作环境、预期结果及实际表现。
- **发布。** 验收后拟在团队仓库建立版本记录，关联源码提交、便携包、原型、测试记录和答辩 PPT。同一版本的说明应写明启动方法、离线功能和模型配置入口。[团队 Release 页面](https://github.com/Ther-ux/qili/releases)
- **答辩与博客。** 拟用同一道残局演示独立落子、规则反馈和本地回放，并准备离线备用路径。现场先讲 PPT 再操作作品，两项合计 10 分钟，随后播放 3–5 分钟 Vlog。阶段结束后依据任务板和验收记录撰写冲刺总结，由队长提交。
