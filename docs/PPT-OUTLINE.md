# 《棋理学伴》项目汇报 PPT 大纲

源码版本：v0.2.10。此文件是汇报草案；当前功能和验收数据以 `SUBMISSION.md`、`README.md` 及最新测试结果为准。

建议采用 **10 页主汇报＋3 页答辩备用页**，主汇报控制在 **10 分钟**，另预留 **6 分钟问答**。页数为组织建议，不是老师规定。

作业依据：[2026 秋软工实践团队作业——第一次（团队展示＋选题报告＋需求分析）](https://edu.cnblogs.com/campus/fzu/202601SofwareEngineering/homework/16758)。

第 2 页的调研和第 8 页的模型对比，需要补入真实材料；团队资料及分工按实际情况填写。

## 第 1 页｜棋理学伴：面向象棋初学者的战术学习助手

**时间：45 秒**

- 项目定位：帮助初学者理解短局面中的走法、规则与战术。
- 产品理念：先独立落子，再通过提示和讲解理解原因。
- 展示团队名称、成员、角色分工及团队合照。
- 一句话介绍团队目标。

**画面建议：** 项目标志＋完整棋盘界面截图，团队信息放在下方。

## 第 2 页｜需求调研：初学者在哪一步卡住？

**时间：60 秒**

- 目标用户：了解部分基础规则、希望学习短战术的象棋初学者。
- 待验证的问题：
  - 知道推荐走法，却不理解原因。
  - 容易混淆炮架、马腿、应将等规则。
  - 做错以后缺少有针对性的再次练习。
- 展示实际访谈或试玩反馈，说明哪些需求得到支持。
- 从调研中提炼优先解决的问题。

**画面建议：** 用户场景图＋1—2 条真实反馈。

**准备材料：** 实际调研对象、记录及结论。

## 第 3 页｜产品范围：围绕一次完整的学习过程

**时间：50 秒**

核心学习过程：

选择题目 → 独立走棋 → 获得判定 → 查看提示或讲解 → 错题重练

- 20 道自编教学题：8 道基础题、12 道残局题。
- 提供分类、主题筛选、分级提示、规则小册和学习记录。
- 多步残局由黑方自动应将，完成最终绝杀才计通关。
- 当前不做完整自由对弈、在线匹配和长将长捉裁定。

**画面建议：** 学习流程图，旁边列出本期范围与非本期范围。

## 第 4 页｜需求分析：功能与验收如何对应？

**时间：65 秒**

| 用户需求 | 对应功能 | 验收重点 |
| --- | --- | --- |
| 练习基础规则和战术 | 基础题、残局题 | 合法性及训练目标判定正确 |
| 卡住时获得帮助 | 三级提示、本地解法回放、AI 讲解 | 提示递进，来源清楚 |
| 回顾自己的错误 | 错题本、重练 | 错误可记录，完成后更新状态 |
| 保留学习进度 | 本地存储、导入导出 | 刷新不丢失，多标签页不覆盖 |

补充非功能需求：

- 操作清晰，支持键盘和小屏浏览。
- 请求失败有提示，不展示旧结果冒充新结果。
- API Key 不写入学习记录，模型调用由用户主动触发。

**画面建议：** 简化功能分解图＋验收表。

## 第 5 页｜领域智能体：规则、工具与模型如何协作？

**时间：90 秒**

处理流程：

用户着法 → 规则检查与目标判定 → 按题目标签选择相关知识 → 可选调用 Pikafish → 组织教学提示并调用模型 → 检查可显示结构、生成一致性提醒 → 展示讲解

说明各部分职责：

- **规则工具：** 判断合法性、将军、绝杀及题目目标。
- **Pikafish：** 提供棋力参考分析。
- **大模型：** 根据已有证据组织教学解释。
- **程序校验：** 损坏结构明确报错；可显示但引用或措辞不一致时先展示原文并提醒，回放线路始终由本地工具提供。

定制方式：规则知识整理、标签检索、工具调用、教学提示与流程编排；当前没有进行模型微调。

**画面建议：** 一张智能体流程图，用不同颜色区分规则、引擎和模型。

## 第 6 页｜系统设计：前后端分工与开源复用

**时间：50 秒**

- 前端：棋盘操作、题库筛选、讲解展示和学习记录。
- 后端：题库、可信判定、证据生成、引擎调度和模型请求。
- 浏览器存储：保存学习进度，支持同来源多标签页同步。
- 外部服务：DeepSeek API；本地工具：Pikafish。

说明复用与新增内容：

- 复用开源象棋规则、记谱模块和 Pikafish 引擎。
- 项目新增教学题库、训练目标、多解判定、多步训练及讲解流程。

**画面建议：** 系统结构图，下方标注开源来源与许可。

## 第 7 页｜运行演示：从走对一步到理解残局

**时间：90 秒**

演示三个片段：

1. **基础练习**
   - 选择一道题，完成走棋。
   - 展示合法性与目标判定反馈。
2. **两步残局**
   - 红方首步正确后，黑方自动应将。
   - 展示最终绝杀才计完成。
3. **学习反馈**
   - 展示分级提示、AI 讲解或错题重练。
   - 展示独立完成与提示后完成的区别。

**画面建议：** 现场操作为主，准备清晰截图或短录屏作为备用。

## 第 8 页｜定制效果：在相同条件下比较

**时间：70 秒**

比较设置：

- 同一模型、局面、候选着法及规则／引擎证据。
- 基础组：通用提示。
- 定制组：增加相关规则知识、教学案例和分步解释要求。

展示一个代表性案例的两份真实输出，并从以下方面点评：

- 规则与战术事实是否正确。
- 是否解释了实际候选着法。
- 引用证据能否支持结论。
- 初学者能否理解并复现。

**画面建议：** 左右两栏真实输出，用少量标注指出差异。

**准备材料：** 真实对照结果及人工点评，目前不填写提升比例。

## 第 9 页｜测试与优化：保证核心过程可靠

**时间：45 秒**

已完成的检查：

- 172 项自动测试通过，包含模拟模型接口与真实本地引擎检查。
- 20 道教学题全部通过可解性检查。
- 覆盖多解接受、多步残局、非法历史和模型异常等情况。

重点修复：

- 多标签页记录互相覆盖。
- 请求失败错误影响独立完成判定。
- 引擎故障连带阻止模型讲解。
- 摆谱调用状态不同步、切题残留旧提示、回放核验资料归属不清。

**画面建议：** 精简测试结果＋一组修复前后说明。

**讲述重点：** 软件正确性测试与模型教学效果评测是两类不同的验证。

## 答辩备用页（不计入 10 分钟主讲）

### 备用页 A｜为什么需要大模型，而不是只用象棋引擎？

- 引擎提供搜索和棋力参考。
- 规则工具负责可核验的判定。
- 大模型负责组织面向初学者的解释。
- 项目价值需要通过真实用户反馈和对照案例验证。

### 备用页 B｜模型出错、断网或引擎不可用怎么办？

- 基础训练、本地提示与解法回放不依赖模型调用；详细逐步讲解由 DS 提供。
- 模型失败明确提示，不伪装成成功。
- 引擎不可用时，讲解明确降级为规则证据。
- 输出结构校验不等于自然语言解释完全正确。

### 备用页 C｜需求文档与后续实施依据

- 功能思维导图。
- 核心类图及关键数据关系。
- 功能—验收标准对应表。
- 团队分工、需求迭代记录与资料来源。
