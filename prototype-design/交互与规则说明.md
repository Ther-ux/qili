# QILI 棋理学伴 · 交互与规则说明

版本：原型1.0 / 2026-11-09。项目基线：qili-study-personalized v0.3.0。桌面1440×960，移动端390×844。

## 1. 产品与设计意图

目标用户为中国象棋初学者，学习任务是“先独立走一步，再理解这步的目的、规则和变化”。默认展示9–12岁初学者的慢节奏讲解。目标用户是项目设定，未假称已完成真实用户访谈或教学效果测量。

设计采用棋院式的暖白与墨绿，朱红区分红方，木色棋盘提供空间焦点。主要内容遵循“任务目标 → 棋盘 → 即时反馈 → 按需提示/教练”的顺序。教练先回应用户自己的想法，再给具体依据，最后留下一个自检问题。所有模型文案均为原型人工编写样例。

桌面固定228宽导航，内容区双栏布局；移动端先棋盘后反馈。主要按钮44像素高，状态通过文字及颜色共同表达。移动端为三张专项设计页面，并非把桌面界面压缩替代移动设计。

## 3. 用户主任务

### A. 自主训练与错题闭环

1. 总览进入题库，按主题找到“隔一子，才是炮”。
2. 目标：用红炮一步吃掉b7黑车。棋盘固定红方坐标，红炮b2、炮架红车b4、目标黑车b7。
3. 点b2选择红炮；点b7完成。点b6进入非法落点反馈，棋盘不执行非法着法。
4. 提示逐级从规则观察、具体炮架到示例坐标。提示后达标进入“提示后完成”，无提示达标进入“独立完成”。
5. 失败尝试进入错题记录；完成后可重练、看本地解法或主动请求教练复盘。

演示入口：首页“继续练习”。错误反例用b2→b6：炮隔过b4后不能落在空点；正确为b2→b7隔一子吃敌车。

### B. 领域Agent与软件功能结合

| 环节 | 软件提供什么 | Agent/用户交互如何体现 |
| --- | --- | --- |
| 用户表达 | 当前题、最近尝试、是否借助提示、最多240字的计划 | “我想借红车做炮架，吃掉黑车” |
| 重建与核验 | 服务端重建实际棋盘，验证着法；客户端自报结果不作权威 | 等待界面展示棋盘重建与规则证据准备状态 |
| 领域检索 | 按cannon标签检索炮架条目与自编教案 | 讲解引用“恰好一个炮架”，证据芯片可进入本地回放 |
| 可选引擎 | Pikafish参考着法与变化，来源独立显示 | 不用引擎分值替代训练任务判定，不换算未经校准的胜率 |
| 个性化解释 | 学习年龄段、水平、目标、节奏 | 用短句聚焦b4红车，解释术语“炮架” |
| 输出与时序 | 检查结构与一致性，绑定局面版本 | 等待、成功、有提醒、失败；过期结果不覆盖新棋盘 |
| 用户追问 | 同一任务下的回答数据 | 一个自检问题：“如果中间有两枚棋子，还能吃吗？” |
| 回到软件验证 | 本地回放、合法落点、自由摆谱 | 黑将e9→d9的独立分支，再主动分析当前局面 |

Agent负责讲解、回应计划与提出自检问题；走棋合法性、明确目标及可回放线路由确定性工具提供。定制方式为知识检索、工具调用、提示编排、结构化上下文与输出检查，未微调模型权重。

### C. 图片/FEN残局研究

导入 → 选择原图方向 → 标记左上、右上、右下、左下四个最外侧交叉点 → 裁剪识别与字形复核 → 标出可疑棋位 → 用户修正 → 勾选人工确认 → 本地分析 → 用户按需请求AI讲解。

“未确认”和“已确认”用两张状态页呈现，未确认状态不能进入分析。示例局面为帅车合力封宫：黑将d9、红帅e0、红车e7，红方先行；本地参考首着e7→d7。不把识别文本直接当作正确棋盘或判胜依据。原型通过示例图片演示，不读取和上传真实图片。

### D. 回放与摆谱

解法回放的“走前/走后”只切换观察局面；不返回作答状态、不改成绩。走后局面另开摆谱，黑将e9→d9作为合法探索分支，回到红方行棋。分支不写入原题答案与统计。走棋不调用模型；点击“AI分析当前局面”才展示当前分支的讲解样例。

## 4. 规则目录与验收点

| ID | 规则 | 触发与界面反馈 | 对应页 |
| --- | --- | --- | --- |
| R00 | 演示与实现边界 | 评审播放器标注演示数据；后台标注新增设计；不调用真实模型 | 导览、工作台 |
| R01 | 合法性独立判定 | 非法不落子；合法未达目标不计完成；不同正确解均接受 | 训练、非法反馈、编辑 |
| R02 | 明确训练目标 | 将杀=正在将军且无合法应对；困毙不算本题绝杀；未发现短杀不等于必输/和棋 | 分析、规则页、知识 |
| R03 | 逐级提示与解法 | 提示1观察，提示2具体位置，提示3示例；查看答案视为借助提示 | 三级提示、回放 |
| R04 | 成绩分类 | 独立完成与辅助完成分别记；最终绝杀才计多步通关 | 完成、错题 |
| R05 | 记录归属 | 浏览器本地学习统计，不当作测得的棋力；可备份迁移 | 总览、错题 |
| R06 | 模型主动调用 | 改偏好、走棋、查看本地解法不触发模型；按钮请求可能产生费用 | 等待、设置、摆谱 |
| R07 | 四种调用状态 | 等待、成功、有提醒成功、失败分别可见；失败清除旧AI结果，保留局面与工具记录 | 11–15 |
| R08 | 异常与补写 | 网络/结构失败不自动重试、不自动揭答案；内容一致性提醒保留原文，不因此强制付费补写 | 提醒、失败 |
| R09 | 局面绑定 | 固定红方a0坐标；翻转不改坐标；请求绑定局面版本，过期结果丢弃；模型文字不能改变棋盘线路 | 回放、摆谱、记录详情 |
| R10 | 图片人工确认 | 先校准方向和角点；冲突保留提示，不猜补帅将；人工确认后可分析 | 导入18–21 |
| R11 | 数据最小化 | 只存学习偏好枚举；Key仅当前页内存；自述仅用于相关请求，不写入公开诊断 | 档案、API、后台 |
| R12 | 连接状态真实性 | 应用设置不等于测试成功；清除后停用；刷新要重输 | API设置 |
| R13 | 内容发布门槛 | 草稿→核验→预览→发布；FEN、行棋方、目标、参考解、正确解集合与提示必须一致 | 后台26–29 |
| R14 | 管理与审计 | 内容管理员维护题库/规则，运行审查使用脱敏请求元数据；不展示Key，不虚构集中用户档案 | 后台25–32 |
| R15 | 触控与阅读 | 移动端先棋盘后反馈，主按钮44px高；焦点可见、状态有文字 | 移动33–35 |

对应现有约束：自由摆谱最多80步；单客户端每分钟最多30次分析；模型讲解单次最多等待120秒，失败不自动重试。图片识别最多3次模型调用。原型中的等待流程由评审者选择状态进行演示，不假装真实等待结果。

## 5. 后台角色与必要范围

后台是本轮新增设计，不声称已有可用接口或认证系统。必要的登录校验应作为后台入口前置条件，当前采用“已进入内容管理员工作台”的设计场景。

| 场景 | 内容管理员 | 只读审查者（拟定权限） |
| --- | --- | --- |
| 查看题目、规则、脱敏运行记录 | 允许 | 允许 |
| 保存题目/教案草稿 | 允许 | 不允许 |
| 运行可解性与规则核验 | 允许 | 只查看结果 |
| 发布通过核验的新版本 | 允许，需确认 | 不允许 |
| 查看真实Key或儿童身份资料 | 不提供此能力 | 不提供此能力 |

发布保留版本与操作者、时间、规则核验摘要等审计信息；历史记录仍指向原题版本。结构失败与一致性提醒分开审查。记录详情显示结构化局面、命中的规则标签、证据、提示版本、模型与检查结果；用户侧可追溯到对应提醒。

## 8. 验证与使用范围

交付包含专用工具保存和重新打开记录、原生页面渲染、全部43页的视觉缩略图、热点目标及边界检查，以及10条主要交互链路的真实浏览器检查。检查结果见 `qa/verification.json`。这些证明原型可演示，不证明真实模型教学效果或现有产品新增功能已经实现。

参考项目保留的边界：未实现完整棋谱导入、整盘比赛复盘、在线对战、语音、完整残局库和长将长捉裁定；不使用虚构的访谈、模型评测百分比或用户效果数据。
